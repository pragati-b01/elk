## 1. Overall POC flow

The architecture separates the solution into clear security and processing boundaries:

* **User-facing file transfer** is handled through the Public Inbound/Outbound SFTP locations.
* **Microsoft Defender** provides malware scanning before files are allowed into the private processing area.
* **Azure Functions** act as the controlled bridge between public and private storage zones.
* **Private Inbound/Outbound locations** isolate files from direct user access to internal processing areas.
* **Pollers** handle file movement between the Azure/private area and the existing on-premises environment.
* **Local Dropbox and EDI** allow the existing EDI process to continue without major changes.
* **Service accounts and SSH keys** provide application-to-application authentication rather than relying on individual user accounts.
* The outbound path follows a similar controlled model in reverse.

That separation is a **strong point for the POC**, especially because it allows the existing EDI process to remain largely unchanged.

# 2. User access and permissions

### Questions to clarify

* Who creates the user's SFTP account?
* Is each user given an individual SFTP account, or is an account shared by a group/application?
* Are users restricted to **only their assigned inbound/outbound folders**?
* Can a user see files uploaded by other users?
* Can a user delete or overwrite files?
* Are users allowed to upload only, or upload/download/delete?
* How are users removed or disabled when they leave the organization?
* Is there an existing process for password/SSH-key rotation?
* Is MFA required for the user-facing SFTP connection, or is authentication only through SSH key/password?
* Is the Public Inbound SFTP exposed directly to the internet, or is access restricted through VPN/IP allowlisting?

### Strong design point

The user should ideally **never have access to the Private Inbound/Outbound locations**.

The separation should be:

> **Public SFTP = user access**
> **Private SFTP = system-to-system access**

That gives you a much cleaner security boundary.

# 3. Poller design

This is probably one of the **most important areas to discuss in the POC**.

The Poller is effectively the bridge between Azure and the existing on-premises environment.

### Questions

* Where exactly does the Poller run?

  * On-premises server?
  * Jump server?
  * Dedicated Windows server?
* Does it run as a Windows Service?
* What account runs the Windows Service?
* Does that account have access only to the required folders?
* How frequently does the Poller check the Private Inbound location?
* What happens if the Poller is down for 30 minutes, 2 hours, or a day?
* Does it pick up all missed files when it comes back?
* How does it know which files have already been downloaded?
* What happens if a file is partially uploaded when the Poller checks the folder?

### Important issue: duplicate downloads

You should explicitly define the **file lifecycle**.

For example:

```text
Private Inbound
      ↓
Poller detects file
      ↓
Download successfully
      ↓
Move/archive source file
      ↓
Continue processing
```

If the original file remains in Private Inbound after a successful download, the Poller needs another mechanism to know:

> "I already processed this file."

Otherwise, the same file could potentially be downloaded repeatedly.

A better POC question is:

**After successful download, do we move the file to an Archive/Processed folder, or maintain a processing/status mechanism?**

I would strongly favor **moving the successfully downloaded file out of the pickup folder** rather than relying only on filename tracking.

# 4. Trigger design

There are actually **different trigger mechanisms in this architecture**, and they should not be treated as the same thing.

### Inbound

User uploads → Defender scan → Azure Function → Private Inbound → Poller

The Azure portion can potentially be event-driven.

But the Poller is likely **polling-based**.

So you should document:

* What triggers the Azure Function?
* Does Defender completion generate an event?
* Does the Azure Function wait for the Defender result?
* What happens when Defender is still scanning?
* What happens when Defender reports a failure?
* What happens if the Azure Function fails after Defender says the file is clean?

### Poller

The Poller might run every:

* 1 minute
* 5 minutes
* 10 minutes

The interval affects both **performance and user experience**.

For example:

> 5-minute polling means a file may theoretically wait almost 5 minutes before the Poller notices it.

For the POC, define the expected polling interval and why.

# 5. File consistency / partial files

This is an important edge case.

Suppose a 500 MB file is being uploaded to SFTP.

The Poller must **not start downloading the file while the user is still uploading it**.

You need a rule such as:

* File must have a temporary extension during upload, then rename when complete.
* Or Poller checks that file size/timestamp remains unchanged for a defined period.
* Or SFTP platform provides a reliable upload-completion mechanism.

This should be explicitly tested in the POC.

### Question

**How do we guarantee that the Poller only processes completely uploaded files?**

This is probably the biggest gap that diagrams usually don't show.

### Poller failure

* Will it download the same file again?
* How do we prevent duplicate processing?

### EDI failure

If the file reaches Local Dropbox but EDI fails:

* Does the file remain there?
* Is it moved to an error folder?
* Can EDI retry it?

# 8. Retry and idempotency

This deserves its own discussion.

You need to assume that **any component can execute twice** because of retries, restarts, network failures, or timeouts.

Therefore:

> **Moving a file successfully should be safe even if the operation is retried.**

Questions:

* What is the unique identifier for a file?
* Filename?
* Filename + size?
* File hash?
* Transaction/reference ID?
* Is duplicate processing allowed?

For a serious production design, I would consider a **unique file ID/reference** and/or checksum rather than relying purely on filenames.

## The biggest POC validation areas

If you want to keep the discussion **crisp for your team**, I would group everything into these **six areas**:

1. **Security & Permissions** — Are users, service accounts, Poller, Azure Function, and EDI given only the access they need?
2. **File Lifecycle** — How do we prevent duplicate processing and know when a file is completely uploaded?
3. **Triggers & Polling** — What is event-driven versus polling, and what happens when a component is unavailable?
4. **Failure & Recovery** — What happens when Azure, Defender, SFTP, network, Poller, or EDI fails?
5. **Performance & Scalability** — Can the design handle expected file volume, file size, concurrency, and SLA?
6. **Monitoring & Audit** — Can we trace every file from user upload through EDI processing and outbound delivery?

**For the POC, I would consider these more important than simply demonstrating that a file can successfully move from point A to point B.** The POC should prove the **security model, file lifecycle, failure recovery, duplicate prevention, performance, and end-to-end traceability**.
